#### Query patterns and indexes added

| Index | Table | Columns | Query pattern |
|---|---|---|---|
| `idx_tasks_project_status` | `tasks` | `(project_id, status)` | `JdbcTaskRepository.findByProjectId` / `countByProjectId` with `statusFilter != null` |
| `idx_tasks_project_priority` | `tasks` | `(project_id, priority)` | `JdbcTaskRepository.findByProjectId` / `countByProjectId` with `priorityFilter != null` |
| `idx_projects_created_at` | `projects` | `(created_at DESC)` | `JdbcProjectRepository.findAll` — `ORDER BY created_at DESC LIMIT ? OFFSET ?` |

#### Indexes deliberately NOT added

| Candidate | Reason skipped |
|---|---|
| `tasks(project_id, assignee_id)` | `idx_tasks_assignee_id` already covers cross-project assignee lookups; within-project assignee filtering is less frequent than status/priority |
| `project_members(project_id, created_at)` | PK `(project_id, user_id)` already enables efficient project member lookup; member lists are small so in-memory sort is negligible |
| `tasks(project_id, created_at DESC)` | Base `idx_tasks_project_id` handles unfiltered pagination; sort on a bounded result set (already filtered by project_id) is cheap at typical scale |

#### Write-overhead assessment

- `idx_tasks_project_status` / `idx_tasks_project_priority`: 2 extra B-tree entries per task INSERT or status/priority UPDATE. Task management apps read far more than they write; overhead is negligible.
- `idx_projects_created_at`: 1 extra B-tree entry per project INSERT. Projects are rarely created compared to reads.

#### EXPLAIN plan validation

`EXPLAIN` / `EXPLAIN ANALYZE` were not run; the local PostgreSQL instance holds only test data (created by Flyway during development). Query plan verification against representative data volume is noted as a follow-up for a staging environment.
