#### 2. N+1 query — before and after

**The scenario**: listing tasks for a project with the assignee's display name.

`TaskResponse` exposes `assigneeId`. To also show `assigneeName` in the list response a naive approach would be:

```java
// BEFORE — N+1: 1 query for N tasks, then N more for assignee names
List<Task> tasks = taskRepository.findByProjectId(projectId, ...);  // 1 query

// For each of the N tasks that has an assignee, issue a separate SELECT:
tasks.stream().map(t -> {
    String name = (t.assigneeId() != null)
        ? userRepository.findById(t.assigneeId())
                        .map(User::displayName).orElse(null)
        : null;
    return toResponse(t, name);
}).toList();
// Total: 1 + N queries  (e.g. 6 queries for 5 assigned tasks)
```

**Fixed approach** — single LEFT JOIN:

```sql
-- AFTER — 1 query regardless of how many tasks have assignees
SELECT t.id, t.project_id, t.assignee_id,
       t.title, t.description, t.status, t.priority,
       t.due_date, t.created_at, t.updated_at,
       u.display_name AS assignee_name
FROM tasks t
LEFT JOIN users u ON u.id = t.assignee_id
WHERE t.project_id = ?
ORDER BY t.created_at DESC, t.id DESC
LIMIT ? OFFSET ?
```

| | Before | After |
|---|---|---|
| Queries for a page of 20 tasks (10 assigned) | 11 | 1 |
| Round-trips per additional assigned task | +1 | 0 |

**Files changed:**
- `task/api/TaskResponse.java` — added `assigneeName` (nullable)
- `task/infrastructure/TaskWithAssignee.java` — new projection record carrying `Task + assigneeName`
- `task/infrastructure/JdbcTaskRepository.java` — `findByProjectIdWithAssignee()` and `findByIdWithAssignee()` use the JOIN query above; original `findByProjectId()` is kept for update/status pre-fetch operations
- `task/application/TaskService.java` — `listTasks()` and `getTask()` now call the JOIN variants

#### 3. Deliberate transactions

`@Transactional` added to `TaskService` and `ProjectService`:

| Method | Annotation | Reason |
|---|---|---|
| `TaskService` (class default) | `@Transactional` | write operations are wrapped in a transaction by default |
| `listTasks`, `getTask` | `@Transactional(readOnly = true)` | multiple reads share a consistent snapshot; Hikari/PostgreSQL can optimise read-only connections |
| `ProjectService` (class default) | `@Transactional` | same as above |
| `listProjects`, `getProject` | `@Transactional(readOnly = true)` | read-only snapshot across `count + find` calls |

Without `@Transactional(readOnly = true)` on `listTasks`, the two JDBC calls (`countByProjectId` + `findByProjectIdWithAssignee`) could observe different data if a concurrent write lands between them — a subtle inconsistency that is harmless most of the time but hard to diagnose. `readOnly = true` also hints to the connection pool and database that no writes will occur.

Note: `ProjectService.createProject()` calls the `create_project_with_owner` procedure which is already atomic internally. The outer `@Transactional` provides the Spring-managed boundary that covers authorization checks before the procedure call.

---

#### 4. Lazy serialization (JDBC equivalent)

JPA's `LazyInitializationException` does not apply here because TaskFlow uses JDBC, not Hibernate. The equivalent risk is serializing a domain object that carries only foreign-key IDs while the controller caller needs display values — resulting in a front-end that must make N additional API calls to resolve names. The `assigneeName` JOIN above eliminates this need for the task list endpoint.
