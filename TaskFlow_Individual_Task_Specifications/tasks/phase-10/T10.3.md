# T10.3 — Implement Business-Oriented PostgreSQL Stored Procedures

**Task ID:** T10.3  
**Title:** Implement Business-Oriented PostgreSQL Stored Procedures  
**Owner component:** Backend / Database  
**Priority:** Learning objective; follows implementation of the relevant CRUD operations  
**Depends on:** T10.2 and the relevant database schema, migration, and CRUD implementation tasks. Confirm exact task IDs against the master plan.

## Requirement

Implement PostgreSQL stored procedures that encapsulate meaningful database operations, following the business-oriented approach demonstrated by the provided SQL Server `CreateUser` and `GetAllUserStates` examples.

Procedures should support multi-step database operations, enforce appropriate database constraints and rules, manage transaction behavior, handle failures correctly, and return results when required.

Adapt the approach to PostgreSQL and TaskFlow's actual schema rather than copying SQL Server-specific syntax.

## Scope

- Inspect all implemented TaskFlow modules, database tables, repositories, and existing CRUD operations.
- Identify applicable operations across users, projects, tasks, and other implemented entities.
- Design stored procedures around meaningful database use cases, including multi-step operations where appropriate.
- Implement procedures for applicable create, update, and delete workflows across the implemented modules.
- Where appropriate, combine related database changes into one procedure to preserve consistency.
- Implement database-level checks and rely on constraints to protect data integrity.
- Use PostgreSQL transactions and exception handling appropriately. Ensure multi-step changes either complete consistently or roll back on failure.
- Support creation or updating of related records when required by the actual business workflow.
- Return generated IDs, affected-record information, or complete result sets when required by the backend.
- Use PostgreSQL output parameters or suitable JDBC-compatible result-handling patterns.
- Add procedure definitions through version-controlled SQL migrations.
- Refactor the corresponding backend repositories to execute the procedures through JDBC.
- Preserve existing API contracts, domain models, authorization behavior, and application-level validation.
- Document each procedure's purpose, parameters, outputs, business rules, side effects, permissions, and transaction behavior.
- Add integration tests against PostgreSQL for successful operations, validation failures, constraint violations, and transaction rollback behavior where applicable.

## Reference Design Style

Use the supplied SQL Server procedures as behavioral examples:

**`CreateUser` pattern**
- Validate that the relevant relationship does not already exist.
- Verify that required related records exist and are valid.
- Create or update the primary record as appropriate.
- Insert the related record.
- Update associated state when required.
- Return the resulting record.
- Ensure the overall operation is consistent when an individual step fails.

**`GetAllUserStates` pattern**
- Provide a dedicated database routine for a meaningful read operation when the project architecture has a reason to use one.
- Return the expected result set with a clear, stable column contract.

These are design references, not mandatory implementations. Select corresponding TaskFlow use cases based on the real schema and business requirements.

## PostgreSQL Implementation Requirements

- Use PostgreSQL `CREATE PROCEDURE` and `CALL` for stored procedure execution.
- Replace SQL Server-specific constructs such as `TRY/CATCH`, `RAISERROR`, `GETDATE()`, `SET NOCOUNT ON`, and bracket-quoted identifiers with appropriate PostgreSQL equivalents.
- Use PL/pgSQL when procedural control flow, branching, exception handling, or multiple statements are needed.
- Do not issue transaction-control statements inside a procedure without considering PostgreSQL's invocation context and transaction restrictions.
- Use appropriate output parameters or another documented approach for returning results to Java.
- Keep database constraints as the final protection against invalid or duplicate data.
- Use parameterized JDBC calls.
- Keep authorization and application-specific orchestration in the appropriate application layers. Do not assume that moving a workflow into a procedure removes the need for application-level security.

## Work Steps

1. Inspect the current repository, applicable `CLAUDE.md` files, project plan, database schema, migration mechanism, and implemented repositories.
2. Inventory the applicable database operations and identify meaningful procedure candidates.
3. Document each candidate's business purpose, inputs, outputs, validation rules, related changes, and expected failure behavior.
4. Choose the PostgreSQL procedure design and result-handling approach for each candidate.
5. Create new, version-controlled SQL migrations for the selected procedures.
6. Implement the procedures using the actual table names, column types, relationships, and constraints.
7. Refactor the relevant Java repositories to call the procedures using appropriate JDBC APIs.
8. Add PostgreSQL integration tests covering successful execution, duplicate or missing records where relevant, invalid inputs, constraint violations, and rollback behavior.
9. Verify that migrations apply to a clean database and that procedures work through the application.
10. Document the procedure contracts and the division of responsibility between PostgreSQL and Java.
11. Run relevant backend tests and build checks, recording actual commands and observed results.

## Out of Scope

- Copying the supplied SQL Server procedures directly into PostgreSQL.
- Creating procedures for nonexistent or unimplemented modules.
- Forcing every simple query to use a stored procedure without a documented reason.
- Moving all application business logic, authentication, or authorization into SQL.
- Implementing unrelated features or changing unrelated frontend, Redis, or Kafka behavior.
- Modifying previously applied migrations instead of adding new migrations.
- Making unrelated changes to existing user work.
