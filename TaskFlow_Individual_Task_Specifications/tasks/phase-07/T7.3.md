**Notable design decisions:**
- No drag-and-drop (explicitly out of scope). Status is changed via "← Back" / "Forward →" buttons on each task card, which call `PATCH /api/v1/tasks/{taskId}/status`. The backend enforces valid transitions (e.g. TODO → IN_PROGRESS only); invalid attempts surface as a `role="alert"` error above the board.
- The board uses a Server Component page for the initial data fetch and a Client Component (`TaskBoard`) for all interactions. After any mutation (create, move), `router.refresh()` re-triggers the Server Component fetch so the board always reflects server state.
- `fetchTasks` uses `size=100` to load all tasks for the board view. If the total exceeds 100 (due to the server limit), a "Showing N of M" note is displayed and users are directed to use the priority filter.
- Priority filter is URL-based (`?priority=medium`): the Server Component reads it, passes filtered tasks to `TaskBoard`, and `TaskBoard` updates the URL when the select changes — consistent with Next.js App Router conventions and bookmarkable.
- `updateTaskStatus` sends the status value uppercased (`IN_PROGRESS`) since the backend enum expects uppercase.
