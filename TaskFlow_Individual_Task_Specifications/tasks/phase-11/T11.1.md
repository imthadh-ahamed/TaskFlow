#### 1. Error response shape

Every non-2xx response uses `ErrorResponse` (see `common/api/ErrorResponse.java`). The shape matches the contract documented in `README.md`:

```json
{
  "status": 404,
  "error": "Not Found",
  "code": "NOT_FOUND",
  "message": "Project 99 not found",
  "details": [],
  "timestamp": "2026-10-21T13:42:07.123456789Z",
  "path": "/api/v1/projects/99"
}
```

All fields are stable and will not be removed in future releases. The `details` array is non-null (empty for non-validation errors) so callers can always iterate it safely.

---

#### 2. Handler mapping

All cases are mapped in `GlobalExceptionHandler` (`@RestControllerAdvice`):

| Exception | HTTP status | `code` |
|---|---|---|
| `MethodArgumentNotValidException` | 400 | `VALIDATION_ERROR` |
| `ConstraintViolationException` | 400 | `VALIDATION_ERROR` |
| `HttpMessageNotReadableException` | 400 | `INVALID_REQUEST` |
| `IllegalArgumentException` | 400 | `INVALID_REQUEST` |
| `IllegalStateException` | 400 | `INVALID_TRANSITION` |
| `InvalidCredentialsException` | 401 | `INVALID_CREDENTIALS` |
| `SessionRevokedException` | 401 | `SESSION_REVOKED` |
| `TokenValidationException` | 401 | `INVALID_TOKEN` |
| `ForbiddenException` | 403 | `FORBIDDEN` |
| `ResourceNotFoundException` | 404 | `NOT_FOUND` |
| `DuplicateEmailException` | 409 | `EMAIL_ALREADY_EXISTS` |
| `DataIntegrityViolationException` | 422 | `DATA_INTEGRITY_ERROR` |
| `Exception` (catch-all) | 500 | `INTERNAL_ERROR` |

The `InvalidCredentialsException` handler always returns the generic message "Invalid credentials" regardless of what the exception carries — this prevents revealing which of email or password was wrong.

The `DataIntegrityViolationException` handler suppresses SQL details and constraint names; it returns only the generic "verify referenced resources exist" message.

The catch-all `Exception` handler returns only "An unexpected error occurred" — no stack traces, class names, or SQL are exposed to the client. All internal details appear only in server logs.

---

#### 3. Correlation / request IDs

Every error response includes a `X-Request-Id` response header. If the incoming request supplies a `X-Request-Id` header, the same value is echoed back (useful for distributed tracing). Otherwise a random UUID is generated for that response. The request ID is NOT included in the JSON body (keeping the documented shape stable).

---

#### 4. Tests

`GlobalExceptionHandlerTest` (10 tests) uses a dedicated stub controller (`ExceptionHandlerTestController`) to trigger each exception type and asserts on the status code, `$.code`, `$.message`, field details, and `X-Request-Id` header presence. Existing controller tests (`TaskControllerTest`, `ProjectControllerTest`, `MemberControllerTest`) also exercise the handler via real service mock scenarios.

`TaskControllerTest.updateStatus_returns_400_on_invalid_transition` was updated from expecting 500 to expecting 400 with `code = INVALID_TRANSITION`, now that `IllegalStateException` is explicitly mapped.
