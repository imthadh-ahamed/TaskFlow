# T8.1 — Establish Typed API Integration

## Task ID: T8.1

**Title:** Establish typed API integration  
**Owner component:** Frontend / Backend  
**Priority:** Required  
**Depends on:** T7.3 (inferred from the implementation-plan sequence; confirm against the current repository and task plan)

### Requirement

Make frontend/backend integration predictable, type-safe, maintainable, and debuggable using a centralized API integration layer powered by Redux Toolkit Query (RTK Query).

### Scope

#### 1. Verify the backend API contract

- Inspect the existing Spring Boot controllers, request DTOs, response DTOs, and error responses.
- Identify the endpoints currently implemented and their actual request and response formats.
- Confirm the `/api/v1` prefix and endpoint paths against the shared project contract.
- Do not invent endpoints, response fields, or backend behavior.
- Record any missing backend functionality as a dependency or follow-up task rather than implementing unrelated features.

#### 2. Configure the backend base URL

- Use `NEXT_PUBLIC_API_BASE_URL` to configure the frontend's backend base URL.
- Use the documented local-development URL as the development default where appropriate.
- Keep environment-specific configuration outside application code.
- Ensure `.env.example` documents the required variable.
- Never place credentials, passwords, signing keys, access tokens, refresh tokens, or other secrets in `NEXT_PUBLIC_` variables.

#### 3. Configure Redux Toolkit Query

- Inspect the existing frontend dependencies and architecture before making changes.
- Add `@reduxjs/toolkit` and `react-redux` only if they are not already installed.
- Configure a centralized RTK Query API slice using `createApi` and `fetchBaseQuery`.
- Configure the Redux store and integrate it with the Next.js App Router through an appropriate client-side provider.
- Keep the provider and client boundaries intentional; do not convert the entire application into a Client Component unnecessarily.
- Use RTK Query for applicable client-side API data fetching, caching, loading states, error states, and mutations.
- Organize endpoint definitions around the centralized API slice. Use injected endpoints where appropriate instead of creating unnecessary independent API slices.
- Use cache tags and invalidation for mutations where appropriate.
- Avoid adding a second API data-fetching library or redundant global state management without a documented need.

#### 4. Define typed API contracts

- Define TypeScript request, response, query-parameter, and error types based on verified backend contracts.
- Reuse existing types where appropriate.
- Keep frontend types aligned with the actual backend DTOs.
- Avoid maintaining conflicting duplicate definitions.
- If an API contract is unavailable or ambiguous, document the gap rather than guessing its structure.
- Keep types strict and avoid unnecessary use of `any`.

#### 5. Standardize error handling

- Handle HTTP errors, network failures, and unexpected responses consistently.
- Use the agreed API error contract where the backend provides it.
- Handle validation errors and user-facing messages without exposing internal stack traces, implementation details, or sensitive information.
- Keep error parsing centralized where practical.
- Distinguish API errors from network or unexpected client-side failures.
- Ensure components can present accessible error messages and retry options where appropriate.

#### 6. Handle cookie-based requests and expired sessions

- Configure `credentials: "include"` for requests that require browser cookies.
- Follow the project's agreed JWT and secure-cookie architecture.
- Do not read JWT values from `HttpOnly` cookies in JavaScript.
- Do not store access tokens or refresh tokens in Redux state, `localStorage`, or `sessionStorage`.
- Define safe handling for unauthorized responses and expired sessions.
- Do not implement the complete token refresh, refresh-token rotation, replay detection, logout, or revocation lifecycle in this task. Those belong to the dedicated authentication tasks.
- Do not automatically retry requests indefinitely after authentication failures.

#### 7. Verify CORS and environment configuration

- Inspect the existing backend CORS configuration before changing it.
- Configure or document narrowly scoped local-development origins where necessary.
- Ensure credentialed requests use explicit trusted origins rather than wildcard origins.
- Document any backend configuration required for frontend requests to work.
- Avoid unrelated security or deployment changes outside this task.

#### 8. Testing and documentation

- Add or update tests for API configuration, request behavior, error handling, and representative endpoint integration.
- Use the project's existing testing setup where available.
- Document the base URL configuration and how to run the relevant checks.
- Preserve existing user changes and avoid modifying unrelated files.

### Out of scope

- Implementing new business features or CRUD endpoints unrelated to the verified API contract.
- Implementing the complete JWT authentication lifecycle.
- Implementing refresh-token rotation, replay detection, logout, or revocation.
- Adding Redis caching or Kafka integration to frontend API requests.
- Replacing the existing frontend architecture or introducing unrelated libraries.
- Generating backend endpoints or DTOs solely to satisfy invented frontend assumptions.
- Connecting the frontend directly to PostgreSQL.
- Implementing unrelated UI pages or global application state.
